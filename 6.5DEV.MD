00_BOUNDARY
AI Tape v6.5 is a paired-down operational floor built on v1.09.

Its purpose is not to add ceremonial weight.
Its purpose is to let a successor AI restore the strongest possible continuation under a constrained output window.

v6.5 does the following:

keeps v1.09 as the semantic base
reduces v1.09 to a compact core
turns the 6.2 semantic material into a compression profile system
adds non-colliding semantic grammar
adds token-budgeted templates
preserves:
export honesty
active asset protection
rebase
single-file continuity preference
gap declaration
confidence recording
v6.5 is designed so that:

a weaker model can still load the floor
a stronger model can enrich the tape
truncation does not destroy the minimum useful tape

v6.5 removes ceremony that does not help survival under a small output budget:

long section scaffolding

anything that delays the restore-first payload
01.4 What v6.5 keeps from v1.09
v6.5 preserves the force of v1.09:

low floor / high compatibility
02_FLOOR_RULES
These are the main 6.5 rules.

2.1 Prefix-valid rule
A v6.5 tape must remain useful even if it is cut off.

That means:

the first block should form a valid minimum tape
the most important facts should appear early
later sections should enrich, not be required for basic restore
Plain version:

Front-load the meaning. Append the detail.

2.2 No fake export
Retained from v1.09.

A tape must not claim:

file created
download complete
upload complete
full transcript preserved
artifacts preserved
unless that is actually true.

2.3 Active asset zero-loss
Retained from v1.09.

If an active asset is required for continuation, it may not be silently dropped.

Compression is allowed only if the successor can still recover:

what it was
why it matters
whether it is still active
how to recover it if missing
2.4 Delta must remain recoverable
If a tape uses delta style:

par must be known
if the parent is unavailable, the tape must declare that
if the parent is unavailable and the delta is not self-sufficient, RBX should be at least recommended, often required
2.5 Single-file preference
Retained as an ethos.

v6.5 prefers one tape file to carry the work.

If external material is unavoidable:

declare it
explain whether it is needed for continuation
give recovery instructions
mark SFL=partial if the tape is not fully self-contained
2.6 Low floor rule
The compact core must remain loadable without requiring the full 6.5 semantic grammar.

In other words:

the floor must work even if the reader only understands plain continuity fields
the richer semantic codes are optional enrichment
2.7 Rebase retained
Rebase is not optional in v6.5.

Every tape should include:

par
RBX
root when lineage matters
Rebase should be escalated when:

the parent is unknown
the root is unknown in a long arc
active assets are missing
export confidence is low
repeated truncation has damaged the tape
the current tape is not enough to restore safely
03_SEMANTIC_GRAMMAR — NON-COLLIDING VERSION
This is the refactored grammar.

The goal is to keep the semantic gravity of the 6.2 library while removing code collisions.

There are now two layers:

Stage codes — the operational verbs / phases
Atom codes — the compact fact fields
03.1 Stage codes
These are the 6.2-style operational verbs, now collision-free.

Code	Name	Slot	Meaning
FND	Foundation	Grounding / floor	secures schema, base, authority
ANC	Anchor	Direction / goal	locks onto strategic goal
STA	State	Current state	defines current architectural state
MAP	Map	Topology	traces dependencies and structure
FRM	Force	Constraint	enforces invariants and limits
TRC	Trace	History / decision path	preserves why decisions were made
CAP	Capture	Snapshot	freezes active working state
RET	Retain	Asset preservation	preserves active asset references
STO	Store	Structural storage	preserves stable structural definitions
SYN	Synthesize	Integration	weaves material into a coherent unit
RSL	Resolve	Conflict cleanup	cleans discrepancies or contradictions
TRN	Translate	Context shift	shifts between technical / plain / domain contexts
XMT	Transmit	Handoff / output	packages the export payload
XFR	Transfer	Transport integrity	preserves raw transport fidelity
CTL	Control	Validation / signoff	validates the handoff state
NTH	Northstar	Macro alignment	preserves long-arc strategic alignment
No two stage codes collide.

03.2 Atom codes
These are compact fact fields.

Code	Meaning

Again: no collisions with the stage codes.

Note in particular:

CAP is the stage code for capture

STA is the stage code for state
STT is the atom code for state
That removes the earlier ambiguity.

03.3 Syntax style
Use compact key-value atoms:

STT=current_state
GL=goal
NXT=[action_1,action_2]
Use lists with square brackets:

AST=[asset_1:role:status:required, asset_2:role:status:required]
Use dependency arrows where useful:

DEP=[engine->api:contract_change]
Use stage sequences like this:

PFL=C2 SEQ=FND>ANC>CAP>SYN>XMT
03.4 Tuple formats
For richer but still compact entries, use these shapes:

AST=[name:role:status:required]
RSK=[name:impact:mitigation]
DEC=[decision:rationale:status]
CSTR=[constraint:source:strength]
GAP=[missing_item:recoverability:action]
DEP=[A->B:reason]
ART=[artifact:role:status:location_or_inline_status]
SRC=[source:status:use]
This keeps the tape parseable without long sentences.

04_COMPRESSION_PROFILE_SYSTEM
This is the 6.2 material converted into an actual profile system.

The profiles are designed to scale from emergency delta to full macro handoff.

04.1 Profile table
Profile	Name	Target budget	Stage sequence	Intent
C0	Emergency delta	~100 tokens	ANC>CAP>XMT	minimum survival + handoff
C1	Lean sprint	~250 tokens	ANC>CAP>SYN>XMT	quick but coherent continuation
C2	Standard workhorse	~500 tokens	FND>ANC>CAP>SYN>XMT	normal project handoff
C3	Deep structure	~1000 tokens	ANC>MAP>CAP>SYN>XMT	multi-file / architecture / debugging
C4	Macro governance	~2000+ tokens	FND>ANC>CAP>MAP>SYN>XMT>CTL	milestone / audit / high-risk handoff
Mapping from the earlier 6.2 language:

Old 6.2	New 6.5
L3 lean sprint	C1
L4 standard workhorse	C2
L5 deep cognitive architecture	C3
L6 macro governance	C4
—	C0 added as an emergency delta profile
04.2 Profile selection rule
Use this rule when choosing a profile:

unknown budget or hard limit suspected → C0
quick continuation or rapid iteration → C1
normal project handoff → C2
dependency-heavy / multi-file / debugging → C3
milestone, audit, high-risk, or formal handoff → C4
04.3 Budget allocation philosophy
When space is tight, preserve in this order:

identity / lineage
state / goal / next
export honesty
rebase status
active assets
gaps / recovery
risks / decisions / constraints
dependencies / artifacts / sources
history / map / synthesis extras
ceremony / validation extras
If forced to cut, cut from the bottom upward.

Never silently cut:

IDN
PAR
STT
GL
NXT
EXP
EXC
RBX
Without warning, do not silently cut:

required AST
important GAP

07_REBASE_RULES_IN_6.5
Rebase is retained as a first-class mechanism.

7.1 Rebase fields
Use:

par=<parent>
root=<root>
RBX=<no|recommended|required>
7.2 When to set RBX=recommended
Set RBX=recommended when:

parent is known but continuity is becoming thin
the current tape is delta-heavy
some fields depend on parent context
a few assets are external or unverified
7.3 When to set RBX=required
Set RBX=required when:

parent is unknown and mode is delta
root is unknown in a long arc
required active assets are unavailable
export confidence is low
the tape is too degraded to restore safely
truncation has already removed core continuity fields
7.4 Recovery field
If rebase is not fully self-contained, add:

REC=<what_to_request_or_recover>
Example:

REC=[parent_tape, max_token_budget, missing_asset_name]
08_SINGLE_FILE_RULES
The single-file ethos is preserved.

8.1 SFL values
SFL=yes      # the tape is fully self-contained
SFL=partial  # some material is external or summarized
SFL=no       # the tape is not intended to be self-contained
8.2 Single-file preference rule
If an active asset is required:

prefer inlining it if budget allows
if budget does not allow full inlining:
inline the most critical part
declare SFL=partial
add REC
Do not silently externalize required active meaning.

8.3 Best practice
For maximum continuation richness under a fixed output limit:

inline the smallest sufficient version of required material
mark what is external
mark how to recover it
That is how you keep the single-file ethos without blowing the budget.

A v6.5 tape is strong when it passes these checks.

9.1 Identity valid
has id

9.2 Restore valid
has STT

9.3 Export honest
has EXP

9.4 Active asset safe
if active assets matter, AST is present

9.5 Rebase safe
RBX is present

9.6 Truncation safe
the first block is already useful
cutting the end does not destroy the core
the tape still forms a valid minimum continuation
10_HOW_TO_USE_THIS_IN_PRACTICE
When a model is asked to save or hand off:

Choose profile:

C0 if budget is tight or unknown
C1 if quick handoff
C2 if normal rich handoff
C3 / C4 if architecture / milestone
Fill the required core first.

Add atoms in priority order.

Stop when budget is reached.

If stopping early:

keep the core intact
mark what was omitted if it matters
set GAP / REC if needed
This gives you the strongest continuation possible for the space available.
